# Multimodal Prediction of Post-COVID Condition (PCC)

Reproducible analysis pipeline for the paper: *"Pre-Infection Mental Health, but Not Brain Volumetry, Predicts Risk of Post-COVID Condition: A Population-Based Cohort Study in the German National Cohort (NAKO)"*

## Overview

This repository contains the complete analysis pipeline that:

1. **Processes** raw NAKO cohort data (demographics, MRI, lab values, etc.) into analysis-ready Parquet files
2. **Runs** a nested 10×5 cross-validation pipeline with per-modality base learners, stability selection, DML orthogonalization, and XGBoost meta-learner
3. **Generates** all paper figures (evaluation curves, decision curve analysis, modality contributions)
4. **Computes** descriptive statistics and LaTeX tables

The primary PCC outcome is the **Bahmer weighted post-COVID syndrome score** (Bahmer et al. 2022) binarised at `> 10.75`. The central question is one of prediction: whether pre-infection structural brain MRI and baseline mental health predict PCC among the infected, and how each compares against demographics, medical history, laboratory values, and the remaining baseline modalities. The second-hit hypothesis motivates the comparison; its defining vulnerability-by-infection interaction is not identifiable in this design and is not tested here.

## Requirements

- [uv](https://docs.astral.sh/uv/). It installs the Python version itself.
  `.python-version` pins it down to the patch — 3.14.6 — while
  `requires-python` and pyrefly's `python-version` name the 3.14 series, so
  what the type checker checks is what CI runs. The patch is pinned because
  every run stamps its interpreter into `config.csv` and from there into the
  config hash: two machines that ran `uv sync` weeks apart would otherwise
  compute folds under different patch releases and discover it only when
  their merge is refused, hours later.
- Access to the NAKO dataset, for the full analysis only (not included; see
  [Data availability](#data-availability), and
  [Without NAKO access](#without-nako-access) for what runs without it)
- Optional: a TeX distribution. Without one the figures render in
  matplotlib's own fonts instead of the manuscript's, and the `.pgf` output a
  LaTeX document would `\input` is skipped. Everything else runs unchanged.
- The lockfile is resolved for arm64 macOS and x86-64 Linux. Intel macOS is
  deliberately outside it — see `[tool.uv] environments` in `pyproject.toml`
  and DECISIONS §2.20.

## Without NAKO access

The dataset cannot be redistributed, so most readers cannot run the analysis
itself. Everything that does not need it runs from a clean clone:

```bash
uv sync                          # install the pinned environment
make test                        # the test suite                    (~2 min)
make smoke-test                  # one pipeline run on synthetic data (~2 min)
make smoke-supplementary         # the supplementary analyses         (~1 min)
./scripts/run_analysis.sh --smoke  # the complete graph              (~15 min)
```

The fixtures are generated by `smoke_test/` from a distributional profile;
`--smoke` writes to `smoke_data/` and `smoke_results/` and never touches
`data/` or `results/`. **The numbers it produces are meaningless.** What it
checks is that the steps wire together: config loading, the parquet layout,
the modality pipelines, orthogonalization, the meta-learner, the artifact
writer, applying a persisted model to a second cohort, and the supplementary
analyses. That is the same graph the real analysis runs, on data that carries
no signal.

## Running the full analysis

The complete analysis — exactly as performed for the paper — is run by one
command:

```bash
./scripts/run_analysis.sh      # or: make analysis
```

This runs the full graph in dependency order and collects every paper-bound
artifact under **`results/paper/`** (`constants/` for the LaTeX `\newcommand`
files and JSON payloads, `tables/` for the generated LaTeX tables). It
requires NAKO data access configured in `config.toml` and takes **days** —
ten nested 10×5 cross-validation runs dominate the wall-clock, and the two
Lean fits on the large cohorts are most of that. See
[Splitting a rerun across two machines](#splitting-a-rerun-across-two-machines)
for the measured per-configuration times and how to divide them.

> **Reproduction.** Re-running the same command on the same data reproduces
> its results; there is no separate reproduction procedure. Two conditions
> come with that. The library stack has to match — DECISIONS §2.20 measures an
> XGBoost minor release moving 13 of 16 output files, which is why every run
> stamps its versions into `config.csv`. And the XGBoost device has to match:
> it is *detected* rather than configured, so a GPU machine and a CPU machine
> do not reproduce each other. For a fast end-to-end wiring check on synthetic
> data, see [Without NAKO access](#without-nako-access) above.

The graph is:

1. **Data** — `pipeline/01_process_data.py` → `data/processed/`
2. **Pipeline runs** — `pipeline/02_run_pipeline.py` once per configuration,
   each to a deterministic directory under `results/runs/`:
   `primary`, `control`, `neurocog`, `mixed_controls`, `no_dml`, `split_mh`,
   `lean_mri`, `control_lean`, `lean_non_mri`, `lean_pooled`
3. **Transfer** — `pipeline/03_apply_transfer.py` (lean MRI model → non-MRI
   cohort, no refit) → `results/runs/transfer_lean_mri_to_non_mri/`
4. **Figures + statistics** — `pipeline/04_generate_figures.py`,
   `pipeline/05_compute_statistics.py`
5. **Supplementary analyses** — everything under `scripts/supplementary/`

### Pipeline configurations

The primary analysis and its sensitivity variants are all produced by
`scripts/pipeline/02_run_pipeline.py` with CLI flags. `run_analysis.sh` passes
`--output-dir results/runs/<name>` for each; the 10×5 nested CV, stability
selection, and XGBoost hyperparameter search are otherwise identical.

| Configuration | Run dir | Command |
|---|---|---|
| Primary (Bahmer clean-controls + DML) | `primary` | `02_run_pipeline.py` |
| Control (pre-amendment specification) | `control` | `02_run_pipeline.py --without-amendment-features --hyperparam-iterations 10` |
| Neurocognitive-subtype outcome | `neurocog` | `02_run_pipeline.py --target neurocog` |
| Mixed-controls outcome | `mixed_controls` | `02_run_pipeline.py --no-clean-controls` |
| Orthogonalization disabled | `no_dml` | `02_run_pipeline.py --no-orthogonalize` |
| Mental-health sub-modality split | `split_mh` | `02_run_pipeline.py --split-mh-submodalities` |
| Lean classifier, MRI cohort | `lean_mri` | `02_run_pipeline.py --cohort mri --stack lean` |
| Control for the Lean classifier | `control_lean` | `02_run_pipeline.py --cohort mri --stack lean --hyperparam-iterations 10` |
| Lean classifier, non-MRI cohort | `lean_non_mri` | `02_run_pipeline.py --cohort non_mri --stack lean` |
| Lean classifier, pooled cohorts | `lean_pooled` | `02_run_pipeline.py --cohort mri_plus_non_mri --stack lean` |

### Splitting a rerun across two machines

The full graph is days of wall-clock, and it does not divide evenly. The two
Lean fits on the large cohorts dominate it — measured at roughly 25 h
(`lean_non_mri`) and 47 h (`lean_pooled`) against 1.5–2 h for each MRI-cohort
run, since both are fitted on tens of thousands of participants rather than
the imaged subsample. Splitting by configuration is therefore the split that
balances, and `run_analysis.sh` takes it directly:

```bash
./scripts/run_analysis.sh --only lean_pooled    # the long half
./scripts/run_analysis.sh --except lean_pooled  # everything else
./scripts/run_analysis.sh --list                # the step names
```

Selection keeps the guards that a hand-run sequence of `02_run_pipeline.py`
commands loses — the split-MH validation, the control deltas, the constants
snapshot and its diff. A selected step whose input another machine produced
stops and names the directory it needs rather than running on nothing.

Three things have to be equal on both machines, and all three are cheaper to
check before the run than after it:

```bash
# 1. the library stack and the XGBoost device — both are decisive
uv run python -c "from pcc_analysis._gpu_utils import xgb_device; \
from pcc_analysis._provenance import package_versions; \
print(xgb_device()); print(package_versions())"

# 2. the analysis data, per modality, without computing anything
uv run python scripts/pipeline/02_run_pipeline.py --fingerprint-only \
    --cohort mri_plus_non_mri --stack lean
```

The stack follows from `uv sync --frozen` against the same lockfile. The
device is *detected*, not configured: if one machine has a usable GPU and
the other does not, they report `cuda` and `cpu`, every delta across the two
halves is refused, and the fix is to hide the GPU (`CUDA_VISIBLE_DEVICES=`)
on the machine that has one rather than to re-run 46 hours.

**Copy `data/processed/` to the second machine; do not regenerate it there.**
`--only lean_pooled` does not run the `data` step, nothing compares the two
copies during a configuration split, and `lean_pooled` shares its data with
no other run — so a divergence there is caught by nothing. That is what
`--fingerprint-only` is for: run it on both machines with the flags of the
configuration each will compute, and compare the digests by eye.

Afterwards, what each run recorded is in its `config.csv`, and
`scripts/check_run_stacks.py` compares the collected directories:

```bash
make check-runs   # or: uv run python scripts/check_run_stacks.py --runs-dir DIR
```

`run_analysis.sh` calls it at the end of every run, but a partial run can
only see its own half — so run it once more over the collected directories
after copying the two halves together, before any number moves into the
manuscript. The panels that read two run directories at once (transport,
clinical utility, sub-modality) refuse the comparison themselves if the
runs disagree.

For distributed computation *within* one configuration, `--folds 0,1,2`
computes a subset and `--merge-folds DIR` combines the fold artifacts. It
buys less than it looks: the post-CV steps are serial, so splitting the
longest run across both machines saves around 10 % of the makespan over the
configuration split, and it puts folds from two machines into one model.
Two caveats if you do it anyway — copy only the `fold_*.pkl` files, not the
directories, so the fold runs' `provenance.json` is not overwritten; and a
merged run has no `modality_ablation_oos.csv` or
`incremental_performance_oos.csv` (DECISIONS §2.19), which no paper artifact
reads.

The two **control** configurations are not sensitivity analyses. They hold the
specification at the earlier one — the pre-amendment feature set and the
narrower hyperparameter search — so that when a headline moves, the difference
can be attributed to those two choices rather than merely observed.
`run_analysis.sh` prints each control next to the primary run and their
difference.

`control` covers the Full Stack, where both the amendment features and the
widened hyperparameter search apply. `control_lean` covers the Lean Stack, where
only the search width does — the amendment joins are Full-Stack only, but the
search width is global, so the Lean runs and the §A2a transfer built on them
move too.

Three things separate a result under this specification from one produced
before it, and the controls isolate two of them. The third, the dependency
bump, is isolated by measurement instead: DECISIONS §2.20 records that xgboost
3.2.0 → 3.4.0 changes 13 of 16 output files while every other bumped package
leaves them byte-identical. The consequence is worth knowing before reading a
control figure: an earlier number cannot be reproduced under 3.4.0 at all, so
reproducing one end to end takes a run pinned to 3.2.0, and a difference seen
without that pin cannot be attributed to the specification.

Each run directory also carries a `provenance.json` — commit, branch,
working-tree cleanliness, platform, architecture and the library stack —
alongside the `config.csv` that records the analysis configuration. The split
is deliberate: `config.csv` holds everything that decides whether two runs are
comparable — the library stack, the XGBoost device, and a digest of the data
the run was given — and feeds the hash that stops mismatched folds from being
merged; `provenance.json` answers which checkout on which machine produced a
number, which is a different question and no reason on its own to reject
anything.

The run snapshots `results/paper/constants/` before regenerating it and diffs
the two at the end, so it finishes by listing every constant it moved. That
list is the checklist for anything downstream that quotes these numbers: each
one has to be carried over deliberately, because a document that cites them
holds its own edits and cannot simply be overwritten.

### Core pipeline steps individually

```bash
make data          # Process raw CSV → Parquet
make pipeline      # Run the primary nested-CV pipeline
make figures       # Generate paper figures (from the latest run)
make statistics    # Compute descriptive statistics
make supplementary # Supplementary analyses that need no pipeline run dir
```

Code quality checks:

```bash
make check        # lint + format + typecheck + DECISIONS references + tests
make lint         # Ruff linter
make format-check # Ruff formatter, report-only (what CI runs)
make typecheck    # Pyrefly, strict preset
make test         # Pytest
make format       # Auto-format with ruff
make fix          # Auto-fix lint issues + format
```

The same linters run as git hooks. Install them once per clone:

```bash
uv run pre-commit install
```

Ruff (linting and formatting, both autofixing) and pyrefly then run before
each commit, together with a guard against accidentally committing a large
data file. The two ruff hooks write rather than complain: a file that is
unformatted, or carries an autofixable lint error, is repaired in place and
the commit stopped once — `git add` and a second `git commit` then carry the
repaired version, and nobody runs `make format` by hand. CI checks the same
thing report-only (`make format-check`), because a runner can tell you the
tree is unformatted but cannot hand the formatted tree back. Tests are not a
hook at all — they take 85 seconds; CI runs them instead.

The type-check scope and its rationale live in `[tool.pyrefly]` in
`pyproject.toml`. The whole scientific stack is checked, sklearn included;
where sklearn's nominal estimator types and this code's structural ones
(`protocols.py`) do not meet, the compromise is suppressed at the line that
makes it rather than by typing a module as `Any` (see `DECISIONS.md` §2.25).

`make check` runs in CI on every push to `main` and every pull request
(`.github/workflows/checks.yml`). The synthetic end-to-end checks run on the
same events, and on demand from the Actions tab
(`.github/workflows/smoke.yml`): one pipeline configuration, a transfer run
applying that model to the other cohort, and the supplementary analyses the
fixtures can exercise (`make smoke-supplementary`). That set is derived rather
than typed — the Makefile declares every parquet-only analysis once and
subtracts the ones the fixtures cannot reach, naming the reason for each — so
it cannot drift from what actually runs. This is the only executable check
possible on a runner, since the real analysis needs NAKO access. The Python
version is pinned in `.python-version`; dependencies are pinned exactly in
`pyproject.toml` and installed from `uv.lock` with `uv sync --frozen`.

## Where the reasoning lives

Three documents, and they answer different questions:

- **`DECISIONS.md`** — every methodological and technical decision in the
  pipeline, with the rationale and, where one exists, the measurement behind
  it. Ordered by pipeline stage. The code cites it by section number, and
  `make check` verifies that every citation resolves.
- **`docs/preprocessing.md`** — what happens to each variable between the raw
  NAKO export and the model: sentinel handling, derived columns, the encoding
  of every questionnaire block.
- **`docs/classifier_configuration.md`** — the per-modality base learners,
  their penalties and solvers, and why each is set the way it is.

Start with `DECISIONS.md` if you want to know *why* something is the way it
is, and with `docs/` if you want to know *what* the pipeline does to a
particular variable.

## Data availability

The analysis uses data from the German National Cohort (NAKO
Gesundheitsstudie). **The data are not in this repository and cannot be
redistributed.** They are available to researchers on application to NAKO, in
line with its use-and-access policy; see
[nako.de](https://nako.de/) for the procedure. The work here was carried out
under approved NAKO data use application **NAKO-882**, which is the identifier
a few of the extraction modules refer to where a variable's coding is specific
to that delivery.

What this repository contains is the analysis code, the design decisions
behind it, and a synthetic-data path so the pipeline can be inspected and
exercised without the data. What it does not contain is any participant-level
data, any derived participant-level artifact, or any result file: `data/`,
`results/`, `smoke_data/` and `smoke_results/` are all untracked.

`smoke_test/profiles/default.json` is the one file derived from the real data.
It holds per-column marginal distributions used to shape synthetic fixtures —
means, standard deviations, missingness fractions and category proportions
across 928 variables, each rounded to three significant figures. It contains no
minima or maxima, no cross-tabulations, no row or column counts, and no
participant-level value of any kind; see `smoke_test/profiles/README.md`.

NAKO participants gave written informed consent, and the study was approved by
the ethics committees of the participating institutions.
